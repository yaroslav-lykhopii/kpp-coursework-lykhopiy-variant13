ВСТУП
Актуальність розроблення інформаційної системи зумовлена необхідністю автоматизованого зберігання, опрацювання та відображення даних, пов’язаних із технічним обслуговуванням готельного комплексу. Використання програмної системи дає змогу впорядкувати відомості про номери, фахівців та заявки на ремонт, контролювати процес виконання робіт та вести облік витраченого часу. Централізоване зберігання взаємопов’язаних даних і автоматизоване виконання основних операцій спрощують їх опрацювання та зменшують кількість ручних дій користувача.
Курсова робота передбачає створення клієнт–серверної кросплатформеної інформаційної системи мовою Java. Графічний інтерфейс користувача реалізується засобами JavaFX, взаємодія клієнтської та серверної частин здійснюється через HTTP із передаванням даних у форматі JSON, а зберігання даних забезпечується реляційною базою даних MySQL. Серверна частина будується з використанням Servlet API та розподілу відповідальностей між рівнями Service і DAO. У системі також передбачено фоновий CSV-імпорт засобами JavaFX Task, валідацію даних, обробку помилок, логування та автоматизоване тестування JUnit 5.
Метою курсової роботи є розроблення клієнт–серверної кросплатформеної інформаційної системи технічних заявок готельного комплексу мовою Java з графічним JavaFX-клієнтом, серверною частиною на Servlet API та зберіганням даних у MySQL.
Для досягнення поставленої мети необхідно виконати такі завдання:
– сформувати предметну модель системи, що охоплює сутності Номер, Фахівець, Заявка та Запис виконання, визначити їх основні властивості та зв’язки;
– спроєктувати клієнт–серверну архітектуру програмної системи та реляційну модель бази даних;
– створити базу даних MySQL і SQL-сценарій для відтворення її структури та початкових демонстраційних даних;
– реалізувати серверну частину системи з використанням моделей даних, DAO/JDBC, Service та Servlet і забезпечити HTTP/JSON-взаємодію з клієнтською частиною;
– реалізувати JavaFX-клієнт для створення, перегляду, редагування та видалення даних основних сутностей;
– реалізувати чотиристанний життєвий цикл заявки: НОВА (NEW) → ПРИЗНАЧЕНА (ASSIGNED) → В_РОБОТІ (IN_PROGRESS) → ВИКОНАНО (DONE) із перевіркою допустимості переходів між станами;

1 ПОСТАНОВКА ЗАДАЧІ ТА ВИМОГИ ДО СИСТЕМИ
1.1 Характеристика предметної області
Варіант №13 передбачає розроблення інформаційної системи технічних заявок готельного комплексу. Система орієнтована на реєстрацію номерів готелю, облік фахівців (технічного персоналу), створення заявок на усунення несправностей та фіксацію виконаних робіт. Основний інформаційний потік починається з виникнення несправності в номері, що потребує створення заявки та призначення фахівця. Основний інформаційний потік починається з виникнення несправності в номері готелю. Для усунення проблеми створюється заявка, у якій вказується номер, заголовок, опис та оцінки впливу (F1, F2, F3). На основі цих оцінок серверна частина обчислює інтегральний показник впливу. Заявці може бути призначений фахівець (технічний працівник).
Подальше опрацювання попередження здійснюється через послідовну зміну станів. Подальше опрацювання заявки здійснюється через послідовну зміну станів. Після призначення фахівця заявка переходить у стан «В роботі», а після завершення ремонту — у стан «Виконано». Із заявкою можуть бути пов’язані записи виконання, у яких фіксуються дата, коментар та витрачені години. Такий зв’язок дозволяє простежити шлях від виникнення несправності до її усунення.

Тому одна й та сама перевірка спрацьовує незалежно від того, чи запис створено вручну через JavaFX, чи отримано під час CSV-імпорту.

Для перетворення Java-об’єктів у JSON та назад використовується ObjectMapper з бібліотеки Jackson. 2 ПРОЄКТУВАННЯ СИСТЕМИ
2.1 Клієнт–серверна архітектура
Архітектура системи побудована так, щоб графічний інтерфейс, HTTP-взаємодія, предметна логіка і SQL не змішувалися в одному класі. Основний маршрут передавання даних наведено на рисунку 2.1.
 
Рисунок 2.1 – Архітектура програмної системи
JavaFX-клієнт відповідає за введення та відображення даних. Він звертається до HotelClient, який формує HTTP-запити. Servlet приймає запит, зчитує параметри і передає операцію до Service. Service перевіряє дані та виконує предметні правила, після чого звертається до DAO. DAO містить SQL-запити і працює з MySQL через JDBC. У зворотному напрямку Servlet перетворює результат у JSON, а клієнтський ObjectMapper відновлює Java-об’єкти.
Така схема забезпечує практичний розподіл відповідальностей: зміна SQL не потребує перенесення SQL-коду в GUI; правила життєвого циклу не дублюються в JavaFX; клієнт не знає параметрів підключення до MySQL. Це також дозволяє окремо тестувати розрахункову і сервісну логіку.
2.2 Розподіл відповідальностей між рівнями
Таблиця 2.1 – Ролі основних рівнів системи
Рівень	Відповідальність	Не повинен містити
JavaFX	Відображення даних, введення, реакція на дії користувача.	SQL, пряме підключення до MySQL, правила переходів станів.
HotelClient	Формування HTTP GET/POST, кодування параметрів, перетворення JSON.	Предметні правила та SQL.
Servlet	Отримання HTTP-параметрів, виклик Service, формування JSON-відповіді.	SQL і основну предметну логіку.
Service	Валідація, предметні правила, інтегральний показник, життєвий цикл, логування.	GUI та HTTP-деталі.
DAO/JDBC	CRUD-запити, PreparedStatement, перетворення ResultSet у моделі.	GUI, HTTP і правила життєвого циклу.
MySQL	Постійне зберігання стану системи.	Логіку Java-застосунку.

Для звичайної операції додавання маршрут має вигляд: JavaFX-форма → клієнтська модель → HotelClient → POST → Servlet → Service → DAO → MySQL. Після успішного виконання клієнт повторно завантажує актуальний список даних із сервера. Таким чином, TableView не розглядається як локальне сховище.

3.2 Моделі та DAO/JDBC
Серверні модельні класи відображають структуру предметних сутностей у Java-коді. Room містить id, number, floor, type і status; Specialist — fullName, specialization і phone; Ticket — roomId, specialistId, title, description, state, F1–F3 і impactIndex; WorkRecord — ticketId, performedAt, comment і hoursSpent. Для стану використовується окремий enum TicketState.
public enum TicketState {
    NEW, ASSIGNED, IN_PROGRESS, DONE
}
DAO-рівень виконує безпосередню взаємодію з MySQL. Для кожної основної сутності використовується окремий DAO. Параметри SQL передаються через PreparedStatement, що відокремлює текст SQL від значень та спрощує повторне використання однакових операцій.
String sql = "INSERT INTO room(number,floor,type,status) VALUES(?,?,?,?)";
try (Connection c = DBUtil.getConnection(); PreparedStatement p = c.prepareStatement(sql)) {
    p.setString(1, r.getNumber());
    p.setInt(2, r.getFloor());
    p.setString(3, r.getType());
    p.setString(4, r.getStatus());
    p.executeUpdate();
}
Для читання даних DAO виконує SELECT, отримує ResultSet і перетворює кожний рядок на відповідний Java-об’єкт. Методи getById використовуються сервісними класами для перевірки існування пов’язаних записів перед виконанням предметної операції.
3.3 Service-рівень, валідація і логування
Service-рівень є центральним місцем для предметних правил. Саме тут перевіряється коректність даних, наявність пов’язаних об’єктів, обчислюється інтегральний показник, контролюються переходи станів і фіксуються основні операції в Logger. DAO викликається лише після успішної перевірки.
Таблиця 3.1 – Основні перевірки Service-рівня

6.1 Нормування факторів та формула
У підрозділі 1.4 визначено предметний зміст факторів F1–F3, що використовуються для оцінювання впливу заявки. Далі наведено порядок підготовки факторів та розрахунку інтегрального показника у серверній частині системи.
F1, F2 і F3 надходять разом із даними заявки у вже нормованому вигляді та перевіряються на належність діапазону 0–100.
Інтегральний показник для всіх варіантів обчислюється за формулою:
I = 0,40 · F1 + 0,35 · F2 + 0,25 · F3.
Обчислення винесене в клас ImpactCalculator, а викликається із TicketService під час створення або перерахунку Ticket. Користувач не вводить I вручну.

I = 0,40 · 50 + 0,35 · 60 + 0,25 · 70 = 58,50.
Отже, TicketService створює заявку із значеннями F1 = 50, F2 = 60, F3 = 70 та impactIndex = 58,50. Саме ці значення відображаються у JavaFX-клієнті. Результати обчислень для інших заявок наведено в таблиці 6.1.

Життєвий цикл заявки (Ticket) реалізовано за допомогою переліку TicketState та перевірки допустимості переходів у класі TicketService. Послідовність переходів показано на рисунку 6.1.
 
Рисунок 6.1 – Чотиристанний життєвий цикл заявки варіанта №13

6	assignedToInProgressAllowed() — ASSIGNED → IN_PROGRESS	true — перехід дозволено
7	inProgressToDoneAllowed() — IN_PROGRESS → DONE	true — перехід дозволено
8	newToDoneRejected() — NEW → DONE	false — перехід заборонено
9	roomValidationWorks() — number = ""	IllegalArgumentException
10	ticketValidationWorks() — f1 = 120	IllegalArgumentException
Перші чотири тести перевіряють математичну частину предметної логіки. Тест riskCalculationWorks() підтверджує, що для значень F1=50, F2=60 та F3=70 інтегральний показник I дорівнює 58.5. Тест riskCalculationWithMaxFactors() перевіряє коректність розрахунку при максимальних значеннях факторів (100, 100, 100), де I = 100.0.
Наступні чотири тести перевіряють правила життєвого циклу заявки. Переходи NEW → ASSIGNED, ASSIGNED → IN_PROGRESS та IN_PROGRESS → DONE повинні бути дозволені, тому відповідні перевірки очікують значення true. Перехід NEW → DONE пропускає проміжні стани і є недопустимим, тому для нього очікується значення false.
Останні два тести перевіряють базову валідацію вхідних даних. Тест roomValidationWorks() передає об’єкт Room із порожнім номером, а тест ticketValidationWorks() — об’єкт Ticket зі значенням F1, що дорівнює 120 і перевищує допустиму верхню межу. В обох випадках очікуваною реакцією є виникнення IllegalArgumentException, а не помилку самого тесту.
Наведені модульні тести перевіряють логіку, яка не потребує безпосередньої взаємодії з MySQL, Tomcat або JavaFX. Тому їх можна виконувати незалежно від запуску інших компонентів системи. Для запуску всього набору тестів серверної частини в каталозі server використовується команда:
mvn test
Фактичні результати виконання набору тестів наведено в підрозділі 7.2.

7.2 Результати тестування
Тести можна запускати безпосередньо з IntelliJ IDEA або за допомогою Maven. Для запуску всіх тестів серверної частини у терміналі необхідно перейти до каталогу server, у якому розташований файл pom.xml, і виконати команду:

8 ІНСТРУКЦІЯ ЗАПУСКУ
8.1 Підготовка MySQL
Перед запуском серверної частини необхідно запустити MySQL і виконати database.sql. Скрипт створює базу hotel_tickets, таблиці room, specialist, ticket та work_record і початкові демонстраційні записи.
У DBUtil перевіряються URL, ім’я користувача та пароль локального MySQL. Для реалізованого проєкту URL має вигляд jdbc:mysql://localhost:3306/hotel_tickets. Якщо локальні облікові дані відрізняються, вони коригуються перед запуском.
8.2 Складання та запуск серверної частини
У терміналі необхідно перейти до каталогу server, де знаходиться server/pom.xml, і виконати:
mvn clean package
Maven компілює серверний код, запускає 10 тестів JUnit 5 і створює server/target/hotel-tickets-server.war. WAR копіюється до каталогу webapps Apache Tomcat 9.x. Після цього Tomcat запускається командою startup.bat із каталогу bin.
Перед запуском JavaFX-клієнта сервер перевіряється у браузері за адресою:
http://localhost:8080/hotel-tickets-server/rooms
За коректної роботи браузер отримує JSON-масив номерів. Ця перевірка підтверджує, що Tomcat розгорнув WAR, RoomServlet прив’язаний до /rooms, сервер має доступ до MySQL і JSON-відповідь формується коректно.
8.3 Запуск JavaFX-клієнта
Після перевірки сервера у терміналі IntelliJ IDEA перейти з кореневого каталогу курсової роботи до каталогу client:
cd client
Переконатися, що в цьому каталозі знаходиться файл pom.xml, і виконати:
mvn javafx:run
Після цього має відкритися головне вікно JavaFX-клієнта (вікно «Готельний комплекс - Управління». Для коректної роботи CSV-імпорту клієнт запускається з каталогу client, щоб відносний шлях sample-data/rooms.csv. вказував на наявний файл. На цьому етапі сервер Apache Tomcat і база даних MySQL повинні залишатися запущеними, оскільки JavaFX-клієнт отримує та змінює дані через серверну частину.
8.4 Контрольний сценарій перевірки
Повна перевірка виконується у такій послідовності:
1.	Переконатися, що MySQL запущений і база hotel_tickets створена з database.sql;
2.	Виконати mvn clean package у server та перевірити успішне виконання 10 тестів;
3.	Розгорнути hotel-tickets-server.war у Tomcat 9.x і перевірити /rooms у браузері;
4.	Запустити JavaFX-клієнт командою mvn javafx:run;
5.	Перевірити CRUD для номерів, фахівців, заявок та записів виконання;
6.	Створити заявку і перевірити автоматичне обчислення I;
7.	Послідовно виконати NEW → ASSIGNED → IN_PROGRESS → DONE та переконатися, що NEW → DONE відхиляється;
8.	Запустити CSV-імпорт і перевірити ProgressBar, статус «Готово. Імпортовано: 2» та появу двох нових номерів;
9.	Переконатися, що основні операції й помилки фіксуються Logger, а користувацькі помилки відображаються у JavaFX.
 
ВИСНОВКИ
У курсовій роботі розроблено клієнт–серверну інформаційну систему технічних заявок готельного комплексу як повну реалізацію варіанта №13. Система побудована мовою Java 21 і складається з JavaFX-клієнта та серверного Web-модуля, який розгортається в Apache Tomcat 9.x.
Реалізовано чотири основні сутності та CRUD-операції для них (Номер, Фахівець, Заявка, Запис виконання). Дані зберігаються в MySQL, а доступ до БД виконується через DAO/JDBC. Предметні правила, валідація, логування, розрахунок інтегрального показника та контроль життєвого циклу розміщені на Service-рівні. Servlet відповідає за HTTP-взаємодію і JSON-відповіді, а JavaFX-клієнт не має прямого доступу до MySQL.
Для заявки реалізовано чотиристанний життєвий цикл із перевіркою дозволених переходів. Інтегральний показник обчислюється за трьома факторами в діапазоні 0–100; F1, F2 і F3 надходять із даними заявки, а інтегральний показник розраховується на сервері. Фоновий імпорт номерів реалізовано через JavaFX Task із ProgressBar і текстовим статусом, тому графічний інтерфейс не блокується під час читання CSV та HTTP-запитів.
Створено 10 тестів JUnit 5 для перевірки розрахунків, правил переходів і валідації. Проєкт збирається Maven-командами, використовує відносний шлях до CSV та може бути відтворений на іншому комп’ютері після створення БД із database.sql і налаштування локального підключення до MySQL. Отже, усі основні вимоги індивідуального завдання реалізовані в єдиному наскрізному програмному рішенні.
